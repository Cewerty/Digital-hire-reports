# Прототип рабочего пространства наставника

## 1. Цель и границы

Создать интерактивный фронтенд-прототип для идеатона, демонстрирующий сценарий:

> Профиль и интервью → Чтение отчёта → Правка → Утверждение документа.

Основной результат — полноценный внутренний отчёт наставнику, сохраняющий структуру и выразительность предоставленного пользователем примера.

Прототип работает на вымышленных данных полностью в браузере.

### Реализовать

* просмотр профиля кандидата и материалов интервью;
* просмотр заранее подготовленного отчёта;
* просмотр источников каждого раздела;
* редактирование реквизитов и шести разделов отчёта;
* предпросмотр Markdown;
* сохранение черновика;
* утверждение документа;
* сохранение состояния между переходами по страницам.

### Не реализовывать

* интеграцию с 1С;
* Python-бэкенд, API и БД;
* реальную генерацию через LLM;
* авторизацию;
* внешний профиль работодателя;
* автоматическую оценку кандидата;
* отдельную форму решения «Принять / Отказать»;
* ENUM для статуса кандидата и вердикта;
* автоматическую проверку согласованности статуса, выводов и вердикта;
* привязку источников к отдельным предложениям;
* визуальный rich-text-редактор;
* хранение изменений после перезагрузки страницы.

Не добавлять фиктивную генерацию, загрузку из 1С и искусственные задержки.

### Не добавлять без необходимости

Для состояния достаточно `useState` и `props`.

## 5. Формат отчёта

Не заменять документ короткими аналитическими карточками.

### Заголовок

```text
Отчёт по кандидату: Имя (предпочитаемое обращение)
```

### Реквизиты

В указанном порядке:

1. Кому.
2. Интервьюер.
3. Контакт.
4. Дата контакта.
5. Направление.
6. Куратор.
7. Статус.

Поле «Статус» — свободная текстовая рекомендация по кандидату, например:

> Рекомендован в основной состав подготовки.

Это не состояние документа.

### Разделы

Названия и порядок фиксированы:

1. Краткое резюме кандидата.
2. Описание кандидата.
3. Навыки кандидата и его опыт.
4. Требования, желания или мотивация кандидата.
5. Будущие уточнения и процессы на следующие этапы.
6. Выводы.

### Поддерживаемое содержимое

Внутри разделов:

* абзацы;
* маркированные списки;
* вложенные списки;
* нумерованные списки;
* жирное выделение;
* курсив;
* цитаты;
* обычные ссылки.

В шестом разделе сохраняется свободная структура с плюсами, рисками и вердиктом. Не выделять вердикт в отдельный обязательный селектор.

## 6. Модель данных

```typescript
type DocumentState = "draft" | "approved";

type ReportSectionId =
  | "summary"
  | "description"
  | "skills"
  | "motivation"
  | "next_steps"
  | "conclusions";

interface Candidate {
  id: string;
  fullName: string;
  preferredName: string;
  course: number;
  group: string;
  specialty: string;
}

interface InterviewEntry {
  id: string;
  question: string;
  answer: string;
}

interface ReportMetadata {
  recipients: string;
  interviewer: string;
  contact: string;

  // YYYY-MM-DD для работы с input type="date".
  contactDate: string;

  direction: string;
  curator: string;

  // Свободный текст, не ENUM.
  candidateStatus: string;
}

interface ReportSection {
  id: ReportSectionId;

  // Тело раздела без его основного заголовка.
  markdown: string;

  // Ссылки на исходные материалы интервью.
  sourceEntryIds: string[];
}

interface CandidateReport {
  candidateId: string;
  candidateDisplayName: string;
  metadata: ReportMetadata;
  sections: ReportSection[];
  documentState: DocumentState;
}
```

Названия разделов и их порядок хранить отдельной константой:

```typescript
const REPORT_SECTION_DEFINITIONS = [
  { id: "summary", title: "Краткое резюме кандидата" },
  { id: "description", title: "Описание кандидата" },
  { id: "skills", title: "Навыки кандидата и его опыт" },
  {
    id: "motivation",
    title: "Требования, желания или мотивация кандидата",
  },
  {
    id: "next_steps",
    title: "Будущие уточнения и процессы на следующие этапы",
  },
  { id: "conclusions", title: "Выводы" },
] as const;
```

### Важные различия

* `metadata.candidateStatus` — содержание отчёта.
* `documentState` — состояние проверки документа.
* Вердикт — Markdown внутри раздела `conclusions`.
* Утверждение документа не означает автоматического приёма кандидата.

## 7. Демонстрационные данные

### Основной документ

Использовать предоставленный пользователем отчёт как образец структуры, подробности и подачи:

* развёрнутое резюме;
* организационные условия;
* технический опыт с уточнениями;
* ожидания от наставника;
* конкретные следующие шаги;
* плюсы, риски и вердикт.

Не сокращать его до прежних четырёх абзацев.

Для публичной демонстрации использовать вымышленные имена и явно фиктивный контакт. Не переносить настоящий Telegram-контакт из примера.

### Материалы интервью

Подготовить согласованные вымышленные ответы, покрывающие:

* опыт React, Vite и Tailwind;
* обучение программированию;
* использование Bash и Git;
* отсутствие доступных старых репозиториев;
* знания блокчейна;
* отсутствие практики Solidity;
* использование кошельков;
* доступное время и график;
* мотивацию участия в соревнованиях;
* ожидания от наставника;
* организационные вопросы.

Каждый ответ имеет постоянный ID.

### Достоверность формулировок

Различать:

* сообщение кандидата о себе;
* фактически проверенный навык;
* интерпретацию наставника;
* прогноз.

Не представлять самоотчёт как подтверждённую компетенцию.

Не выводить автоматически «высокую дисциплину» из заявленного количества свободных часов. Прогноз сильного результата должен читаться как предположение, а не установленный факт.

## 9. Страница отчёта `/report`

### Структура

```text
Отчёт                                               [Черновик документа]

Демонстрационный отчёт подготовлен заранее.

┌────────────────────────────────────────────────────┐
│ Отчёт по кандидату: ...                            │
│                                                    │
│ Кому: ...                                          │
│ Интервьюер: ...                                    │
│ Контакт: ...                                       │
│ Дата контакта: ...                                 │
│ Направление: ...                                   │
│ Куратор: ...                                       │
│ Статус: Рекомендован ...                           │
│                                                    │
│ 1. Краткое резюме кандидата                         │
│ Оформленный текст                                  │
│ [Источники раздела · 3]                            │
│                                                    │
│ ...                                                │
│                                                    │
│ 6. Выводы                                          │
│ Плюсы, риски, вердикт                              │
│ [Источники раздела · 5]                            │
└────────────────────────────────────────────────────┘

[← Профиль]                                   [Перейти к проверке →]
```

### Рендеринг Markdown

Создать общий компонент `MarkdownContent`, использующий `react-markdown`.

Пример:

```tsx
<div className="prose prose-slate max-w-none">
  <ReactMarkdown skipHtml>{markdown}</ReactMarkdown>
</div>
```

Текстовую колонку ограничивать внешним контейнером, чтобы `max-w-none` не приводил к чрезмерно длинным строкам.

Требования:

* не использовать `dangerouslySetInnerHTML`;
* не подключать обработку сырого HTML;
* не включать `rehype-raw`;
* сохранять стандартную безопасную обработку URL;
* не превращать каждый обычный перенос строки в `<br>` без необходимости.

Основные заголовки разделов выводятся приложением, а не хранятся внутри Markdown-полей.

### Источники раздела

После каждого раздела показывать кнопку:

> Источники раздела · N

При нажатии раскрывается блок под этим разделом:

* номер или обозначение ответа;
* вопрос интервью;
* полный исходный ответ.

Использовать простое раскрытие через React-состояние либо Collapsible. Popover и подсветка отдельных предложений не нужны.

Повторное нажатие сворачивает блок.

Если источников нет, показывать:

> Источники раздела не указаны.

Не создавать фиктивные ссылки.

### Пояснение источников

Один раз на странице вывести:

> Материалы помогают проверить раздел, но не подтверждают автоматически каждую его формулировку.

### Утверждённое состояние

При `documentState === "approved"`:

* показывать «Документ утверждён наставником»;
* отображать сохранённую версию;
* кнопку перехода назвать «Повторная проверка и правка».

Не менять текст статуса кандидата автоматически.

## 10. Страница проверки `/review`

### Реквизиты

Показывать отдельные подписанные поля:

* имя в заголовке отчёта;
* кому;
* интервьюер;
* контакт;
* дата контакта;
* направление;
* куратор;
* статус кандидата.

Для статуса кандидата использовать обычный `Input` или `Textarea`, не `Select`.

Редактирование имени в документе не должно автоматически переписывать исходный профиль кандидата: это отдельные данные прототипа.

### Шесть разделов

Каждый раздел — отдельная область:

```text
3. Навыки кандидата и его опыт

[Редактирование] [Предпросмотр]

┌─────────────────────────────────────────────┐
│ Markdown-поле / оформленное содержимое       │
└─────────────────────────────────────────────┘

[Источники раздела · N]
```

Требования:

* по умолчанию открыт режим редактирования;
* переключение режима не теряет введённый текст;
* предпросмотр использует тот же `MarkdownContent`, что и страница отчёта;
* `Textarea` достаточно высокая для содержимого;
* разрешено изменение её высоты пользователем;
* шесть разделов расположены последовательно;
* можно независимо просматривать и редактировать разные разделы.

Добавить короткую подсказку по Markdown:

> `**жирный**`, `*курсив*`, `- пункт списка`, `1. следующий шаг`.

### Источники при редактировании

Источник раздела доступен для чтения, но его привязки в прототипе не редактируются.

Вывести пояснение:

> После правок проверьте, что материалы раздела по-прежнему обосновывают его содержание. Привязки источников автоматически не обновляются.

Не пытаться анализировать текст или автоматически проверять выводы.

### Нет отдельной формы решения

Не добавлять:

* «Принять / Отказать»;
* оценку пригодности;
* числовые баллы;
* отдельный вердикт вне документа;
* автоматическую синхронизацию статуса и выводов.

Наставник меняет рекомендации непосредственно в содержимом отчёта.

## 11. Действия формы

### «Отменить»

* удалить несохранённые изменения рабочей копии;
* перейти на `/report`;
* не изменять сохранённый документ.

### «Сохранить черновик»

* проверить заполненность обязательного содержимого;
* сохранить рабочую копию;
* установить `documentState: "draft"`;
* перейти на `/report`;
* показать сообщение:
  > Черновик сохранён в текущей сессии.

### «Утвердить документ»

* проверить заполненность обязательного содержимого;
* открыть `AlertDialog`.

Текст диалога:
> **Подтвердить проверку документа?**  
> Вы утверждаете текущую версию отчёта. Это действие не выполняет зачисление кандидата и не передаёт данные в 1С.

Кнопки:

* «Вернуться к проверке»;
* «Утвердить документ».

После подтверждения:

* сохранить рабочую копию;
* установить `documentState: "approved"`;
* перейти на `/report`;
* показать сообщение:
  > Документ утверждён наставником.

Закрытие диалога не сбрасывает форму.

## 12. Валидация

### Обязательное содержимое

* имя кандидата в заголовке;
* направление;
* непустой Markdown каждого из шести разделов.

Для остальных реквизитов допустимо отсутствие значения. При просмотре выводить «Не указано».

Если дата заполнена, она должна быть корректной.

### Не проверять автоматически

* соответствие статуса вердикту;
* обоснованность рекомендации;
* наличие слов «Плюсы», «Риски», «Вердикт» через поиск по тексту;
* соответствие отчёта требованиям 1С;
* истинность утверждений.

Ответственность за содержательную проверку в прототипе остаётся у наставника.

Ошибки заполнения показывать рядом с соответствующими полями. При неудачной отправке переводить фокус на первое ошибочное поле.

## 13. Организация состояния

### Сохранённая версия

В `main.tsx` хранить текущий `CandidateReport`.

Она используется для:

* просмотра документа;
* отображения состояния документа;
* начального заполнения редактора.

### Рабочая копия

При открытии `/review` создавать независимую копию сохранённого отчёта.

```text
Сохранённый документ
        ↓ открыть редактор
Рабочая копия
        ↓ ввод
Меняется только рабочая копия
        ↓ сохранить / утвердить
Обновляется сохранённый документ
```

Не мутировать вложенные объекты и массивы исходного отчёта.

### Переходы

| Действие | Сохранённый документ |
| :--- | :--- |
| Открыть редактор | Не меняется |
| Ввести текст | Не меняется |
| Переключить предпросмотр | Не меняется |
| Отменить / уйти без сохранения | Не меняется |
| Сохранить черновик | Обновляется, состояние `draft` |
| Утвердить | Обновляется, состояние `approved` |

Открытие утверждённого документа в редакторе само по себе не снимает утверждение.

Сохранение новой версии как черновика снимает утверждение предыдущей версии.

При уходе со страницы без сохранения правки отбрасываются. Предупреждение о несохранённых изменениях не входит в обязательный объём; поведение обозначить рядом с кнопками.

## 14. Возможность перехода к единому Markdown-документу

Текущая версия использует шесть полей, но код не должен связывать хранение данных с конкретной формой редактирования.

Реализовать чистую функцию:

```typescript
function serializeReportToMarkdown(
  report: CandidateReport,
): string;
```

Она объединяет:

* заголовок;
* реквизиты;
* шесть разделов с нумерованными заголовками.

Состояние утверждения и интерактивные блоки источников в содержимое документа не включать.

Не реализовывать сейчас единый Markdown-редактор и обратный парсер.

Это облегчит дальнейший переход к одному полю, но обратное преобразование произвольного Markdown в фиксированные разделы будет отдельной задачей.

## 17. Приёмочный сценарий

1. Открыть профиль и прочитать интервью.
2. Перейти к отчёту.
3. Увидеть реквизиты и все шесть разделов.
4. Раскрыть источники раздела «Навыки кандидата и его опыт».
5. Открыть редактор.
6. Изменить следующий шаг, сохранив нумерованный список.
7. Переключиться в предпросмотр и увидеть корректное оформление.
8. Изменить свободный текст статуса кандидата.
9. Сохранить черновик.
10. Убедиться, что изменения появились в документе.
11. Повторно открыть редактор и утвердить документ.
12. Увидеть состояние «Документ утверждён наставником».
13. Убедиться, что утверждение не изменило статус кандидата и вердикт.
14. Внести новую правку и отменить её — сохранённый документ не должен измениться.
15. Перезагрузить страницу — должны восстановиться исходные демонстрационные данные.

> **Ключевой принцип:** интерфейс обслуживает ваш существующий формат отчёта, а не заставляет переделывать методологию под форму приложения.
