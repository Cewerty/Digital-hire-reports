# Архитектура frontend-прототипа рабочего пространства наставника

## 1. Обзор

Прототип реализует сценарий:

> Дашборд куратора → Реестр кандидатов → Профиль и интервью → Чтение отчёта → Правка → Утверждение документа.

Приложение работает полностью в браузере на вымышленных данных.  
Backend, API, БД, LLM, интеграция с 1С и авторизация отсутствуют.

## 2. Стек

- Vite
- React
- TypeScript (строгий режим)
- React Router
- Tailwind CSS
- shadcn/ui
- `@tailwindcss/typography`
- `react-markdown`
- `lucide-react` — по необходимости

## 3. Маршруты

| Маршрут | Страница | Назначение |
| :--- | :--- | :--- |
| `/` | `CuratorDashboardPage` | Дашборд куратора: профиль, очередь задач, лента событий |
| `/candidates` | `CandidatesListPage` | Реестр кандидатов с фильтрами по этапу отбора |
| `/candidates/:id` | `ProfilePage` | Профиль кандидата и материалы интервью |
| `/candidates/:id/report` | `ReportPage` | Просмотр сохранённого отчёта |
| `/candidates/:id/review` | `ReviewPage` | Редактирование и утверждение |
| `/report`, `/review` | — | Редиректы на `/candidates/c-01/report` для обратной совместимости |
| `*` | `NotFoundPage` | Страница «Не найдено» |

Используется клиентская навигация без перезагрузки страницы.

## 5. Состояние

### Сохранённая версия

Хранится в `AppLayout` через `useState`:

- `reports: Record<string, CandidateReport>` — словарь отчётов по `candidateId`;
- `candidates: Candidate[]` — массив кандидатов;
- `curator: CuratorProfile` — профиль куратора и лента событий.

`AppLayout` — единственный владелец изменяемого состояния. Дочерние страницы
получают данные и колбэки через `useOutletContext<AppOutletContext>()`.
Route loaders не используются: они выполняются вне компонентного дерева React
и не имеют доступа к состоянию хуков.

Используется для:

- просмотра документа;
- отображения состояния документа;
- начального заполнения редактора;
- вычисления метрик дашборда и фильтрации реестра.

### Рабочая копия

При открытии `/review` создаётся независимая копия сохранённого отчёта.

```text
Сохранённый документ
        ↓ открыть редактор
Рабочая копия
        ↓ ввод
Меняется только рабочая копия
        ↓ сохранить / утвердить
Обновляется сохранённый документ
```

Вложенные объекты и массивы исходного отчёта не мутируются.

### Переходы

| Действие | Сохранённый документ | `pipelineStage` кандидата |
| :--- | :--- | :--- |
| Открыть редактор | Не меняется | Не меняется |
| Ввести текст | Не меняется | Не меняется |
| Переключить предпросмотр | Не меняется | Не меняется |
| Отменить / уйти без сохранения | Не меняется | Не меняется |
| Сохранить черновик | Обновляется, состояние `draft` | `reviewed` → `in_review`, иначе не меняется |
| Утвердить | Обновляется, состояние `approved` | `uninterviewed` / `in_review` → `reviewed`; `approved` / `rejected` не меняются |

Открытие утверждённого документа в редакторе не снимает утверждение.  
Сохранение новой версии как черновика снимает утверждение предыдущей версии.

Утверждение документа не является финальным решением по кандидату: этап
переводится в `reviewed` («Рассмотрен»). Финальные этапы `approved`
(«Подтверждён») и `rejected` («Отклонён») выставляются вне прототипа (в 1С)
и не меняются действиями в интерфейсе.

## 6. Поток данных

1. `AppLayout` хранит `reports`, `candidates` и `curator` в `useState` и передаёт их через `<Outlet context={contextValue} />`.
2. `CuratorDashboardPage` читает `candidates` и `curator` из контекста и вычисляет метрики очереди.
3. `CandidatesListPage` читает `candidates` из контекста и фильтрует их по `pipelineStage`.
4. `ProfilePage` получает `candidate` и `interviewEntries` через геттеры контекста.
5. `ReportPage` получает `report` через `getReportById` и отображает его через `ReportDocument`.
6. `ReviewPage` при монтировании создаёт рабочую копию `report`; ключ `key={id}` пересоздаёт компонент при смене кандидата.
7. Редактирование меняет только рабочую копию.
8. При сохранении/утверждении `ReviewPage` вызывает `updateReport` из контекста, который обновляет словарь отчётов, при необходимости — `pipelineStage` кандидата и ленту событий куратора.
9. После сохранения/утверждения выполняется переход на `/candidates/:id/report`.

## 7. Валидация

Обязательное содержимое:

- имя кандидата в заголовке;
- направление;
- непустой Markdown каждого из шести разделов.

Остальные реквизиты могут быть пустыми.  
Если дата заполнена, она должна быть корректной.

Ошибки показываются рядом с полями.  
При неудачной отправке фокус переводится на первое ошибочное поле.

## 8. Markdown-рендеринг

Используется общий компонент `MarkdownContent` на базе `react-markdown`.

Требования:

- без `dangerouslySetInnerHTML`;
- без `rehype-raw`;
- стандартная безопасная обработка URL;
- обычные переносы строк не превращаются в `<br>`;
- основные заголовки разделов выводятся приложением, а не хранятся в Markdown.

## 9. Источники разделов

Каждый раздел имеет `sourceEntryIds: string[]`.

Источники привязаны к разделу, а не к отдельным предложениям.  
При нажатии на кнопку «Источники раздела · N» раскрывается блок с вопросами и полными ответами.

## 10. Ограничения

- Нет сохранения между перезагрузками страницы.
- Нет backend, API, БД, LLM, 1С.
- Нет авторизации.
- Нет отдельной формы решения «Принять / Отказать».
- Нет автоматической проверки согласованности статуса, выводов и вердикта.
- Утверждение отчёта переводит кандидата в этап «Рассмотрен», но не является
  финальным решением: «Подтверждён» и «Отклонён» выставляются вне прототипа.
